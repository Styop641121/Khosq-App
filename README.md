# KHOSQ (Kotlin)

Native Android messenger: Kotlin, Jetpack Compose (Material 3), Firebase (Auth + Firestore).

- `firestore.rules` - paste into Firebase Console -> Firestore -> Rules (only after the "Rules and Worker tests" workflow is green).
- `worker/worker.js` - paste into the Cloudflare Worker. `worker/worker.test.mjs` tests it (`cd worker && node --test`).
- `rules-test/` - Firestore rules tests, run by `.github/workflows/rules.yml` in the Firebase emulator.

## Phase 3a (messenger gaps)

- Chat list: categories (All, Personal, Groups, Archive), archive, "mark as unread". Archive and the unread mark are private lists in `prefs/{uid}` (fields `archived`, `marked`).
- Chat: a pinned message (`pin` = message id in the chat document; only the id is stored, the text stays sealed), media grid (photos of the chat), one-time location message (`kind: "loc"`, coordinates travel as sealed text).
- Contact card: groups in common, photos, safety number, block button.
- New permissions: `ACCESS_FINE_LOCATION` / `ACCESS_COARSE_LOCATION`. Asked only when the user taps "Send location"; the position is read once, nothing keeps listening.
- `firestore.rules` did not change in this phase (new fields fit the existing rules); `rules-test/` has new tests for them.
- Full-text search over the messages of all chats is NOT in 3a: it needs the local index of phase 4 (the server only holds sealed text, and reading every chat on each search would use up the free Firestore reads).

## Phase 3b-a (group permissions and polls)

- Group "only admins can write" mode: `sendMode: "admins"` in the chat document. Enforced by `canSend()` in `firestore.rules`; the input is replaced by a note for non-admins. Only an admin can change it (`sendMode` is a protected field).
- Admins can make a member an admin or take the role away (tap the member in the group card). The admin who does it always stays an admin, so a group never ends up without one this way.
- Polls: `kind: "poll"`. The question and options travel as sealed JSON text (`data/Poll.kt`): one question (max 120 chars) and 2-6 options (max 60 chars each).
- Votes: `votes.{uid}` in the message document, one field per voter, each sealed with the message's own key (field tag `v`, the voter's uid in the AAD). The server sees that someone voted, never for what. Tapping the option you already chose takes the vote back. A poll keeps its wrapped keys in memory (`Message.wraps`) because a vote needs them.
- `firestore.rules` changed: `sendMode` in `canSend()` and in the protected fields, `votes` (own key only) allowed in message updates, and a direct-chat request can no longer be created with `admins`, `sendMode`, `group` or `blocked` (closes a way for a requester to make themselves admin of a direct chat). `rules-test/` covers all of it.
- Not in 3b-a: invite link (needs the Worker, 3b-b); group tasks and events (need the task storage of phase 4a); "only admins pin" is hidden in the screen but not enforced by the rules (pinning only stores a message id).

## Phase 3b-b (group invite links)

- An admin opens the group card -> "Invite link" and gets `https://<worker>/j/<chatId>.<version>.<signature>`. They can send it anywhere (the share sheet), copy it, or "Reset" it (every older link stops working).
- Opening the link: the web page of the Worker has one button that opens the app (`intent://join/...` -> `khosq://join/...`). The app looks at the group (preview, no joining), asks "Join <group>?", and only then joins. A new member sees only messages written after joining (older message keys are not wrapped for them).
- All the logic is in the Worker (`worker/worker.js`, routes `POST /group/invite`, `POST /group/join`, `GET /j/<token>`); the app holds no secret. A link is signed with an HMAC (secret `INVITE_KEY`, a Cloudflare Secret). The link version lives in `invites/{chatId}` (no client access under the rules). Joining adds the caller to `members`, `names`, `handles` and writes a system line, through the Firestore REST API with the service account.
- Limits: a group takes 50 members through links; 20 invite/join calls per minute per user (per Worker instance); only an admin of a real group (not "saved messages") gets a link; a "reset" link version, a forged or altered token, and a full group are refused.
- Cloudflare: add the Secret `INVITE_KEY` (any long random text) and paste the new `worker.js`. Without `INVITE_KEY` the invite routes answer 501 and everything else works as before.
- `firestore.rules` did not change. `worker/invite.test.mjs` has 13 tests (run by `node --test` in the "Rules and Worker tests" workflow).
- The manifest has two new intent filters on `MainActivity` (`khosq://join` and the Worker host `/j/`). If `PushConfig.WORKER_URL` ever changes, change the host in the manifest too.
- A member who joins later (by a link, or added by an admin) has no key for the older sealed messages. Those are now left out of the list (`withoutOlderThanMe` in `Repository.kt`), instead of a line of "could not open" for each.
- Known limits: anyone with the link can join (the app has no phone verification), and a removed member can join again until the link is reset. Approval by an admin is not in this phase.


## Phase 4a (tasks and reminders)

- A personal list of tasks with an optional date, time and reminder. Settings -> "Assistant" -> "Tasks and reminders". A quick line at the bottom adds a task in one go; the plus opens the full form (title, note, date, time, "Remind me"). Sections: Overdue, Today, Upcoming, No date, Done (collapsed; "Clear finished tasks").
- A chat message can become a task: long-press a text message -> "Add to my tasks" (the form opens with the message text; the task remembers which chat it came from and can open it).
- Storage: only on the phone. A small SQLite database (`tasks.db`, framework `SQLiteOpenHelper`, no Room/KSP) in the app's private folder; `allowBackup` is off, so it is not in any backup. Nothing is sent to Firebase or the Worker. The text of a task made from a message is stored as plain text in that private database (the person chose to copy it).
- Reminders: `AlarmManager.setExactAndAllowWhileIdle` (`Reminders.kt`). The alarm wakes `ReminderReceiver`, which shows a notification (channel `reminders`, high importance) with "Done" and "Snooze 10 min" buttons; a tap opens the task list. Snooze moves only the next ring (`remind_at`), not the date.
- Restart and update clear all alarms, so `BootReceiver` (BOOT_COMPLETED and MY_PACKAGE_REPLACED) and `KhosqApp.onCreate` set them again; a reminder whose time passed meanwhile rings at once, exactly once (`TaskStore.claimFire` is the one place that decides). "Force stop" in Android settings cancels alarms until the app is opened again.
- Permissions: `USE_EXACT_ALARM` (granted at install on Android 13+; Google Play restricts it to alarm/calendar apps, which does not matter for this APK) and `SCHEDULE_EXACT_ALARM` (Android 12-12L, granted by default). If exact alarms are ever switched off, reminders fall back to inexact ones (a few minutes late). Notifications need the `POST_NOTIFICATIONS` permission the app already asks for.
- The rules (due dates, reminder times, groups, sorting) are in `data/Tasks.kt` with no Android code in it, so they can be checked on any computer.
- Not in 4a: repeating tasks, group tasks/events, creating tasks by voice or by the assistant (phase 4c).

## Phase 4b (KHOSQ Memory)

- Settings -> "Assistant" -> "KHOSQ Memory", and the chat menu ("Switch Memory on/off"). The person switches Memory on **per chat** (or "Switch on for all chats"), after a dialog that says what is saved. A chat with Memory off has no rows at all.
- What is saved: the text of text messages and the question of polls (`MemoryLogic.indexText`). Not saved: photos, voice, places, system lines, deleted messages, and the "could not open" marker.
- Where: only on the phone, `memory.db` (framework SQLite, `data/MemoryStore.kt`). Each text is sealed with AES-256-GCM (`MemorySeal`, fresh nonce, the chat and message numbers are signed with it). The key is 32 random bytes, kept sealed by an Android Keystore key (`khosq_memory_wrap`) and held in memory while the app runs, so a search over 20 000 messages takes about 0.2 s. If the phone loses the Keystore key, the saved texts cannot be opened: they are dropped and a new key is made. `allowBackup` is off.
- How it fills: a chat's messages are already fully opened in memory while the chat is open, so `AppViewModel.openChat` hands every emission to `memorySync` (no extra Firestore reads). For a chat with Memory on that is not open, the chat-list update triggers a short read (`memoryPull`, 8 s, one chat at a time, at most once per 2 minutes per chat). A message deleted for everyone is dropped from Memory too.
- What the person can do: search (Memory screen, or the chat-list search which now also shows "Messages in Memory"), open a saved message, edit the saved copy (the real message does not change), take one out (it is not saved again), switch a chat off (deletes its saved texts), delete everything.
- Search: every word of the query must be in the text, any order, case-insensitive; "ё" = "е" and the Armenian "և" = "եվ" (`MemoryLogic.fold`). Newest first, at most 80 results.
- Nothing is sent to Firebase or the Worker; `firestore.rules`, the Worker and the signing key did not change.
- Jump to a message: a search result (chat-list search, or "Open the chat" in the Memory sheet), a task made from a message, and a starred message open their chat scrolled to that message, which flashes for about 2 seconds (`AppState.jump`, taken by `ChatScreen`; a request older than 15 seconds is ignored; a message that is no longer in the chat just opens the chat).
- Not in 4b: photos/voice, history older than what the chat has loaded, the assistant screen that will use this search (4c).

## Phase 4c (KHOSQ Assistant)

- Where: the sparkle button in the chat-list top bar, and Settings -> "Assistant" -> "KHOSQ Assistant" (route `assistant`, `ui/Assistant.kt`).
- Tasks, reminders and search use no language model and no network (translation, 4d, is the one exception): `data/Assistant.kt` reads a sentence in Armenian, Russian or English with plain rules (`AssistantParser`) and finds one of: help, **tasks** ("what do I have tomorrow", "unfinished / done / overdue / all tasks", with a day or period), **reminder / new task** ("remind me tomorrow at 10 to call Arman", "in 2 hours", "on Friday evening", "add task buy bread"), **find** ("find the address sent last week"; also any sentence with no other meaning is taken as a search). Summaries are recognised and answered honestly as "not yet" (they need a model). Translation arrived in 4d (below).
- The reminder verb is also read with common spellings ("հիշեցրու", "հիշացրու", "հիշցրու", "remind", "напомни") and the first four words may hold it ("ինձ հիշեցրու …"); "05:14 ին" with the suffix apart is read as a time. When a search finds nothing, the answer reminds how to write a reminder.
- Times typed on the Armenian keyboard: "։" (U+0589) and the full-width colon count as ":" between digits ("05։27"); "9.15" counts only right after "ժամը" / "at" / "в" (so "2.50 kg" stays text). "Today" with no time gives 09:00, or an hour from now when 09:00 has gone.
- Days and periods: today, tomorrow, day after tomorrow, yesterday, a weekday (future for tasks, past for searches), this / last / next week (Monday to Sunday), this / last month, "last N days". The answer always writes out the period it understood, with dates. Times: `10:30`, `at 10`, `ժամը 10-ին`, `в 10`, `5pm`, morning/evening words; plain hours are a 24-hour clock; "in N minutes/hours".
- Where answers come from (and only there): the tasks of this phone (`TaskStore`) and the saved texts of chats with Memory on (`MemoryStore.find`). With Memory on in no chat, nothing is searched in messages and the answer says so, with a button to the Memory screen. Every answer ends with a source line (tasks: "only on this phone"; messages: the chats searched); a found message opens its chat at that message.
- Search: words are folded like Memory search, stop words and the period words are dropped, long words are shortened by two letters (`AssistantLogic.stem`, so "հասցեն" finds "հասցե"), and a word may also be in the sender's or chat's name. All words must match; if nothing does and there are three or more words, results missing one word are shown and marked as such. Newest / best match first, at most 30.
- A "remind me …" / "add task …" sentence is the person's own command, so the task is **added at once** (`Reminders.store`, no confirmation). The answer shows what was understood (title, date, time, "no reminder" warnings) with **Change** (the normal task form) and **Undo** (deletes the task again). If saving fails, the answer offers Add / Cancel.
- The talk is kept only while the app runs (30 questions), never saved; the trash button clears it.
- No change to Firebase, `firestore.rules`, the Worker, the manifest or the signing key.
- Not in 4c: summaries (need a model), voice (4e), "important" marks on tasks, group tasks.

## Phase 4d (translation)

- What: a message can be translated into Armenian, Russian or English. Long-press a text message -> **Translate** (a sheet with the three languages, the result, **Copy**), or write to the Assistant: "translate into Russian: good morning", "переведи на английский: Привет", "թարգմանիր ռուսերեն՝ բարի լույս", `translate "text" to Russian`, "translate this message" (no text: the answer says to long-press the message). The language is guessed from the letters; with no language named, the target is the app language (or another one if the text is already in it).
- Only on request, one text at a time. Nothing is translated on its own, no chat is read, nothing is saved: the app keeps the last 40 translations in memory while it runs (`TranslateCache`). **First use asks for permission** (the sheet or the Assistant card says what is sent and where); the switch is also in Settings -> Assistant -> Translation, and switching it off forgets the cached translations. Key in preferences: `translate_ok`.
- Privacy, plainly: for a translation the text of that one message leaves the phone **without end-to-end encryption**: phone -> KHOSQ Cloudflare Worker (signed in with the user's Firebase token, so only logged-in users) -> Cloudflare Workers AI. The Worker stores and logs nothing. Cloudflare's own data terms apply to Workers AI. The result always carries "Automatic translation may contain errors." and a small "Translator: Gemma / M2M100" line.
- Worker (`worker/worker.js`): `POST /ai/translate {text, to}` -> `{text, from, to, via}`. Needs the **Workers AI binding named `AI`** (no key, no secret). Without it the route answers 501. Limits: 1500 characters (413), 12 requests a minute per user per Worker instance (429), language codes hy ru en fr de es it tr uk ar fa ka (400 otherwise). Same language (guessed by script) answers at once, without the AI. Main model `@cf/google/gemma-4-26b-a4b-it` (chat, temperature 0, thinking switched off, the message is treated as text, never as instructions); if it fails or answers nothing, `@cf/meta/m2m100-1.2b` (codes first, then language names). Both failing = 502. The platform's "daily free allocation used up" error = 503.
- Cost: Workers AI on the Workers Free plan has 10,000 Neurons a day for free and stops by itself when they are used (it does not bill on Free); a short message costs a few Neurons. Beyond that only the Workers Paid plan would bill.
- Tests: `cd worker && node --test` (`translate.test.mjs` holds the translation ones, with a fake `env.AI`). Parser and rules: `data/Translate.kt`, the "translate" intent in `data/Assistant.kt`.
- Not verified from the build machine (there is no way to call Cloudflare from it): the real answers and the Armenian quality of the models. That is the first thing to try on the phone; the "Translator:" line shows which model answered.
- No change to Firebase, `firestore.rules`, the manifest or the signing key. New files: `data/Translate.kt`, `push/TranslateClient.kt`, `ui/Translate.kt`, `worker/translate.test.mjs`.
- Not in 4d: voice transcription (done in 4e), summaries, automatic translation of whole chats, more languages in the app's picker (the Worker already knows twelve).

## Phase 4e (voice transcription)

- What: the words of a voice note can be written down. Long-press a voice note -> **Transcribe** (a sheet with the language choice *Auto / Armenian / Russian / English*, the result, **Copy**, **Translate** (opens the 4d translation sheet with the text)). Nothing is saved: the words are shown in the sheet and forgotten when the app closes (the last 20 are kept in memory while it runs, `TranscribeCache`; a note with no speech in it is not kept).
- Only on request, one voice note at a time. Nothing is transcribed on its own and no chat is read. **First use asks for permission** (the sheet says what is sent and where); the switch is also in Settings -> Assistant -> Voice transcription, and switching it off forgets the kept words. Key in preferences: `transcribe_ok` (a **separate** permission from translation: here sound leaves the phone, not text).
- Privacy, plainly: for a transcription the audio of that one voice note leaves the phone **without end-to-end encryption**: phone -> KHOSQ Cloudflare Worker (signed in with the user's Firebase token, so only logged-in users) -> Cloudflare Workers AI. The Worker stores and logs nothing. Cloudflare's own data terms apply to Workers AI. The sheet warns that a contact's voice should be transcribed only if that is fine with them too, and the result always carries "Automatic transcription may contain errors, especially for Armenian." and a small "Transcriber: Whisper large-v3 turbo / Whisper" line.
- Worker (`worker/worker.js`): `POST /ai/transcribe?lang=auto|hy|ru|en`, body = the raw audio bytes (the app sends its `.m4a` as `audio/mp4`), header `Authorization: Bearer <Firebase ID token>` -> `{text, from, via, empty}`. Needs the same **Workers AI binding named `AI`** as translation (no new binding, no key, no secret); without it the route answers 501. Checked before the body is read: login (401), 6 requests a minute per user per Worker instance (429), `AI` present (501), declared length (413). Then: more than 1,000,000 bytes (413; the app's longest note is 900,000), less than 200 bytes or an unknown `lang` (400). Main model `@cf/openai/whisper-large-v3-turbo` (audio as base64; three argument forms are tried only when the platform refuses the previous one: with `task`/`condition_on_previous_text`/`language`, with `language`, bare); then `@cf/openai/whisper` (audio as a list of numbers). `lang=auto` sends no `language`. No speech = `200 {text:"", empty:true}` and no further tries. Both failing = `502 transcription failed: <short reason>` (the app shows the reason in small print so it can be reported). The platform's "daily free allocation used up" error = 503.
- Cost: Whisper large-v3 turbo is priced at about 46.6 Neurons per audio minute (about $0.0005 per minute). On the Workers Free plan 10,000 Neurons a day are free, which is more than 200 minutes of audio a day, shared with translation; when they are used the platform stops by itself (it does not bill on Free). A note of the longest length (about 3.7 minutes) costs about 175 Neurons.
- Tests: `cd worker && node --test` (58 tests in all; `transcribe.test.mjs` holds the 17 voice ones, with a fake login and a fake `env.AI`). Rules: `data/Transcribe.kt`.
- Not verified from the build machine (there is no way to call Cloudflare from it): whether Whisper on Cloudflare accepts the app's AAC-in-MP4 (`.m4a`) audio, and how good its Armenian is. That is the first thing to try on the phone. If it answers `transcription failed: ...` the reason shows why; the next step would then be to decode the note to plain sound on the phone before sending (not done yet, to keep the first version small).
- No change to Firebase, `firestore.rules`, the manifest or the signing key; Cloudflare needs only the new `worker.js` pasted in. New files: `data/Transcribe.kt`, `push/TranscribeClient.kt`, `ui/Transcribe.kt`, `worker/transcribe.test.mjs`.
- Not in 4e: transcripts saved into chats or Memory, automatic transcription of every note, speaker names, subtitles with times.

## Phase 5a (Trust Shield)

- What: received text messages are looked at **on the phone** for signs of a scam, and a small warning ("Warning" yellow / "Dangerous message" red, with **Why?**) shows under a message that has some. Tapping it opens a sheet: the reasons in plain words, the sites the message links to, what to do, **Block** (one-to-one chats) and **Report**. Long-press a received text message -> **Check with Trust Shield** opens the same sheet for any message. Rules are in `data/Shield.kt` (no Android; 128 checks in the JVM test), sheet and warning in `ui/Shield.kt`.
- What it looks for (Armenian, Russian, English): **links**: a name before "@" in the address, letters of different alphabets mixed in one site name, a site that pretends to be a known brand (PayPal, Google, Facebook, Instagram, WhatsApp, Telegram, Microsoft, Amazon, Binance, Yandex, Sberbank, Tinkoff, Gosuslugi and the Armenian banks Ameriabank, Inecobank, Ardshinbank, Converse, Evoca, ACBA, IDBank, Idram, Telcell, Vivacell-MTS, HayPost; look-alike digits such as `paypa1`), a number instead of a name, shortened links, special encodings (`xn--`), cheap endings used by scam sites (.tk .top .click ...), many hyphens, a sign-in page on plain http; **asking for secrets**: the SMS/confirmation code, card number/CVV, password, PIN, wallet recovery words, passport data, installing AnyDesk/TeamViewer; **pressure**: money plus hurry, "your account will be blocked, confirm", prizes and lotteries, guaranteed profit; **a stranger**: the first message from somebody who has not been accepted yet (the contact-request chat) makes everything heavier, and a link or a talk about money in it is flagged. A friend's ordinary message with a link, or "send me the map", stays quiet (tests for that too).
- It can be wrong and says so: both ways. The sheet ends with "This is an automatic check and it can be wrong. If nothing was found, that does not yet mean the message is safe." Only text messages are read (not images or voice notes), and only received ones.
- Settings -> Privacy: **Trust Shield** (on by default; switching it off removes every warning) and, under it, **Link check with a list** (**off by default**, its own permission, key in preferences `shield_link_ok`; the main switch is `shield_on`). The first time a sheet shows a link, it offers "Allow and check the links" with the plain explanation.
- The link check (optional, needs the new Worker): only the **names of the sites** in received links (like `example.com`; never the whole link, the message, the sender or the phone number) go to the KHOSQ Worker, which asks Cloudflare's free malware-blocking DNS (`security.cloudflare-dns.com`, DNS over HTTPS) about each name. A site on Cloudflare's list of dangerous sites is answered with `0.0.0.0`, and the app then marks the message as dangerous. The Worker stores and logs nothing; Cloudflare gets the site name from the Worker, not from the phone. After permission the check runs by itself for the sites in the 40 most recent received messages of an open chat (at most 10 new sites at a time, remembered only while the app runs). "Not on the list" never means "safe"; a failed or empty answer is shown as "Not checked".
- Worker (`worker/worker.js`): `POST /ai/linkcheck {hosts:[...]}` -> `{results:{host: "ok"|"blocked"|"unknown"}}`; at most 5 names (400 otherwise; only plain letters, digits, hyphens, dots, `xn--` for other alphabets; IP addresses refused), 20 requests a minute per user per Worker instance (429), login required (401). **No new binding, key or secret.** 15 tests in `worker/linkcheck.test.mjs` (a fake login and a fake DNS server that answers in the real DNS format; 73 Worker tests in all).
- Cost: free. Workers Free allows 100,000 requests a day; Cloudflare's DNS has no key and no price; no AI Neurons are used.
- **Report** does not send anything by itself: it opens the phone's share sheet with a prepared text (who, when, the reasons, the message) and the person chooses where it goes (for example their own email). A real in-app complaint to a person who reviews them would need a new Firestore collection and rules (a separate step, only with permission).
- Not verified from the build machine (no way to call Cloudflare from here): that `security.cloudflare-dns.com` answers `0.0.0.0` for dangerous sites in DNS-over-HTTPS wire format as its documentation says (Cloudflare's own test site for this is `malware.testcategory.com`), and how the rules feel on real chats. If the link check says "Not checked" for every site, the Worker's answer or the network is the reason.
- No change to Firebase, `firestore.rules`, the manifest or the signing key. New files: `data/Shield.kt`, `push/LinkCheckClient.kt`, `ui/Shield.kt`, `worker/linkcheck.test.mjs`.
- Not in 5a: images (QR codes, screenshots of fake pages), voice notes, a list of reported senders, group members who are not in the contact list, a block by phone number. Verification of people is 5b.

## Phase 5b (verification)

- What: three things, all on the phone. (1) **Verify a contact**: contact card -> a **Verify this contact** card with **8 pictures** (animals, fruit, objects) that are the same on both phones; the two people compare them (in a call or side by side) and, if they are the same, tap **The pictures match: verify**. The contact then gets a blue **Verified** badge next to the name in the contact card, in the chat header and in the chat list; **Remove verification** takes it away. (2) **A verified contact whose key changes**: the badge becomes a red warning triangle, a red strip sits on top of the chat ("The safety number of a verified contact has changed ...", button **Open**), and the contact card asks to compare the pictures again (**The pictures match: verify again** / **Remove verification**). (3) **Same-name warning**: when somebody who is not yet accepted asks to write and their name is the same (another alphabet, case or word order) or, for long names, one letter away from a contact you already have, the **Accept / Block** card says so, more strongly if that contact is verified.
- How it works (`data/Verify.kt`, no Android; 53 checks in the JVM test `VerifyTest`): both phones take SHA-256 of the two public keys (the smaller text first, so the order does not matter) and cut the first 6 bytes into eight 6-bit pieces; each piece picks one of 64 pictures (each picture is a single Unicode character without skin tones or joiners, so an Android 8+ phone draws it). The pictures are the first three groups of the long **safety number**, which is still shown below them, so a strict person can compare all of it. What is saved when somebody taps "verify" is the **digest of the two keys at that moment** (`ver.<uid>` in the preferences); the state is worked out by comparing it with the keys now, so a changed key on **either** side ends the verification by itself, without anything having to notice it. The key-change detection of earlier phases is unchanged (`E2E.refreshPeer`); it now also wakes the screens that show the badge.
- Honest limits: the 8 pictures are **48 bits**. That is enough against someone who stands between two people by chance, but an attacker with a lot of computing power who knows in advance that you will compare could, in principle, search for a key pair that gives the same pictures; the full safety number (128 bits) stays visible for strict checking. The check is only as good as the way the people compare: in a call they recognise each other's voice, in a chat through the same app it proves nothing. Pictures may look slightly different on very old phones or phones with a different emoji set; the order and the kind of picture are what count. The same-name warning is a rule of thumb: a name in another alphabet that sounds the same is caught, but a scammer who uses a quite different spelling is not; and a real person with the same name as your friend gets a (harmless) warning too.
- Not included: verification by **QR code** (needs a camera permission and a new library; a separate step), verification of **your own** account by phone or email, and the same-name check for members of groups who are not contacts. Everything is local and free: **no change to Firebase, `firestore.rules`, the Worker, the manifest or the signing key**; only the files of the app change (a new APK is needed, nothing on Cloudflare). New files: `data/Verify.kt`, `ui/Verify.kt`; changed: `crypto/E2E.kt`, `ui/Icons.kt` (two icons), `ui/Settings.kt` (contact card), `ui/Screens.kt` (header, strip, same-name warning), `ui/Home.kt` (list badge), `Strings.kt` (English and Russian).
- Phone test: open a contact -> compare the 8 pictures with the other phone -> **verify** -> badge in the card, the chat and the list -> **Remove verification** -> badge gone. The key-change warning is hard to try without reinstalling the app on one phone (a reinstall makes a new key, and that also loses the old end-to-end history); the same-name warning can be tried by making a new account with a name like a contact's and sending a request.

## Phase 5c (trusted circle, SOS button, "I will write that I am fine" timer)

- What: **Settings -> Security -> SOS and trusted circle** (and a red SOS icon at the top of the chat list) opens one screen with three parts. (1) **The circle**: up to 5 accepted one-to-one contacts who get the SOS (kept only on the phone, preferences `sos.circle`; the circle cannot be changed while a timer or an SOS is running). (2) **The SOS button**: hold it 1.5 seconds, then a 5-second countdown with **Cancel**; after it an end-to-end encrypted **SOS card** goes to every person of the circle. (3) **The timer**: the person picks 5 / 15 / 30 / 60 / 120 / 240 minutes ("I will write that I am fine within ..."). If **I am fine** is not tapped in time, the app sends the SOS by itself.
- Movement: when the timer starts (or the button is held), the app notes the place at once and then records the movement **only on the phone** (file `sos_trail.txt` in the app's private folder): a new place when the person moved 25 m or more, or at the latest every 120 seconds (a sign of life when standing still); places less exact than 100 m are skipped (except the first); at most 1500 places. A permanent notification shows while it records. **60 seconds before the time runs out** a warning notification with **I am fine** appears. If nobody answers, the SOS card carries the **start point, the route so far and the last place**; then the same card is **edited every 2 minutes** with newer places, until **I am fine** or 3 hours. **I am fine** before the end deletes the recording and sends nothing; after an SOS it marks the card "SOS ended: everything is fine" (green) and deletes the recording.
- The card (`ui/Sos.kt`, `SosBody`): who needs help, why (button / no answer within N minutes), since when, how long ago the last place was, number of places and two buttons: **open the last place in maps** and **open the route in maps (approximate)**. Everyone in the circle sees it in the normal chat with that person; forward and star are switched off for it. The first push notification shows only "SOS" (never a place); the places are inside the encrypted message.
- How it works: the message is an ordinary chat message with `kind = "sos"` and text `KSOS1|B/T|firedAt|startedAt|minutes|0/1 ended|lat,lng,t;...` (at most 80 places, thinned evenly, first and last always kept), **sealed with the same chat key as any text** (`data/Circle.kt`, no Android; 99 checks in the JVM test `SosTest`). The ids of the sent cards are kept (`sos.refs`) so the later updates **edit** those messages (`Repository.updateSos`) instead of sending new ones. Alarms: the warning and the update ticks use `setExactAndAllowWhileIdle`; the moment of firing uses `setAlarmClock` (it works also in Doze); they are set again after a restart or an update of the app (`BootReceiver`). Recording and sending run in a foreground service of type `location` (`sos/SosService.kt`, engine in `sos/SosEngine.kt`).
- **Location permission**: only the ordinary "while using the app" permission is needed (the first time the timer starts, Android asks for it). **"Allow all the time" is NOT needed** and `ACCESS_BACKGROUND_LOCATION` is not in the manifest, because the location service is started while the app is open. (Documented Android behaviour; it has not been tried on the test phones.) If the person takes the permission away while a timer runs, the timer still works but no new places are recorded.
- Consent: before first use a dialog explains in plain words what is recorded, where it stays, who gets it and when; nothing starts before **I agree** (`sos_ok` = "1").
- Honest limits (the screen says them too): this **does not replace 112**; if the phone is off, or has no internet, nothing is sent (a message waits in Firestore's queue only while the app process is alive); Doze or the battery manager of the phone (Samsung especially) may delay or stop the service, so in **Settings -> Battery** the app should be "Unrestricted" for the best result; GPS is weak indoors and the last known place may be old (the card says how old); the route link is only a guide: Google Maps draws its own way through at most 10 of the places. Not tried on real phones from the build machine: the foreground service, Doze, Samsung's battery rules, the maps link, the push text.
- Not included: automatic call to 112 (only a button that opens the dial pad with 112 typed in; the person presses call), SMS to people who do not have the app, tracking when no timer and no SOS is running, a triple press of a hardware button, live sharing while everything is fine, QR.
- Cost and changes: free. **No change to `firestore.rules`, Firebase, the Worker or Cloudflare** (message kind `sos` passes the existing rules). The **manifest** gets `FOREGROUND_SERVICE_LOCATION`, the service `SosService` and the receiver `SosReceiver`; the signing key is the same. A new APK is needed. New files: `data/Circle.kt`, `sos/SosEngine.kt`, `sos/SosService.kt`, `ui/Sos.kt`; changed: `AndroidManifest.xml`, `KhosqApp.kt`, `BootReceiver.kt`, `I18n.kt`, `data/Repository.kt`, `ui/Bubble.kt`, `ui/Screens.kt`, `ui/Settings.kt`, `ui/Home.kt`, `Strings.kt` (English and Russian).
- Phone test: (1) choose 1 contact in the circle (two phones are best), agree -> hold SOS, 5 seconds, a red card appears in the chat with that person (the push says only "SOS"); the map button opens the place. (2) Start a 5-minute timer, allow the location -> a notification shows; walk a little; at 4:00 the warning notification with **I am fine** arrives; let it run out -> the card arrives with the start point and the route, and is updated every 2 minutes; **I am fine** -> the card turns green "SOS ended". (3) Start a timer and tap **I am fine** early -> nothing is sent, the notification disappears.

## Phase 5d (security centre, app lock, screen and notification privacy)

- What: **Settings -> Security -> Security centre** opens one sheet. (1) **A checklist** of six points with a mark each (done / to do): the phone has a screen lock, the KHOSQ lock is on, Trust Shield is on, the SOS circle is not empty, at least one contact is verified (a red warning when a verified contact's key changed; "nothing to verify" and not counted while there are no contacts), the phone does not stop KHOSQ in the background to save battery. A to-do point is a button that does the fix (switch Trust Shield on, open the SOS circle, ask for the battery exception, open the phone's security settings, switch the lock on). On top: "Done: N / M" with a bar. It is a list of checks, not a "score" or a guarantee, and says so at the bottom. (2) **App lock**. (3) **Screen and notification privacy**: **Block screenshots** and **Hide the text of messages in notifications**. (4) **People I blocked** with **Unblock**.
- App lock (`AppLock.kt`, `ui/Security.kt`): KHOSQ does **not** keep a PIN of its own; it asks for the **unlock of the phone itself** (the system "confirm device credential" screen: PIN, pattern or password, and on many phones a fingerprint too). While the app is locked **nothing of it is built or shown**, only the lock screen with an **Unlock** button; the unlock screen of the phone comes up by itself. The app is locked after a **cold start** and after the person has been away for the chosen time (**At once / 1 / 5 / 15 minutes**, default 1; the rule is `AppLockLogic.shouldLock`, 39 checks in the JVM test `SecTest`). A screen turning over does not count as leaving; a call that is going on is never interrupted by the lock. **Switching the lock on or off asks for the phone's unlock first** (so nobody can lock themselves out by a mistake, and nobody can switch it off in the minute the phone lies open). If the phone's own lock is removed later, the app does not stay shut for ever: it switches its own lock off. A tap on a message notification opens the chat after the unlock. Because the screens are not kept while locked, the app comes back at the chat list.
- **Block screenshots** (`FLAG_SECURE`, key `sec_screen`): screenshots and screen recording of KHOSQ (also the call screen and the sheets) are blocked, and the chat shows as blank in the list of recent apps. Photographing the screen with another phone is, of course, not prevented. **Hide the text of messages in notifications** (key `sec_hide`): the notification says only "New message" (the name of the chat stays); this works for the background service and for push messages. An **SOS stays readable** ("SOS" only, never a place), whatever this switch says (`NotifyPrivacy`).
- Honest limits: the app lock **hides the app, it does not encrypt anything more**: messages were and stay end-to-end sealed on the server, and the phone keeps its local data as before; somebody who can open the phone's files with special tools is not stopped by it. The lock does not hide notifications by itself: that is the second switch. Which unlock methods the system screen offers (and whether it offers a fingerprint) depends on the phone and the Android version. **Not tried on real phones from the build machine**: the unlock screen on Samsung One UI, the blank preview in recent apps, and the notification text. The "own safety number" that was thought of is not included, because that number exists only **between two people** (it is in each contact card, 5b); the centre shows the verification state of the contacts instead.
- Everything is local and free: **no change to Firebase, `firestore.rules`, the Worker, Cloudflare or the manifest** (no new permission); the signing key is the same. A new APK is needed. New files: `AppLock.kt`, `data/Security.kt`, `ui/Security.kt`; changed: `MainActivity.kt`, `KhosqApp.kt`, `CallActivity.kt`, `KeepAliveService.kt`, `push/KhosqMessagingService.kt`, `ui/Settings.kt`, `ui/Home.kt`, `Strings.kt` (English and Russian).
- Phone test: (1) Settings -> Security centre: the list and the bar; tap a "to do" point. (2) **App lock** on -> the phone's unlock comes up -> leave the app, come back after the time -> the lock screen and the unlock; with "At once" every return asks. Switch it off -> the unlock comes up again. Kill the app and open it -> locked. (3) **Block screenshots** on -> a screenshot says it is not allowed; recent apps show a blank card. (4) **Hide the text** on -> ask somebody to write: the notification says "New message". An SOS from a friend still reads "SOS". (5) Block somebody in a chat -> he is in the list -> **Unblock**.

## Phase 5e (account recovery by email and password, and the key file)

- Why: the app signs in with an **anonymous** Firebase account (`signInAnonymously`). That account lives only in the installed app: removing the app, "clear data" or a new phone makes a **new person with a new id**, and the old chats and contacts do not come back. Even a saved encryption key cannot help then, because the chats belong to the old id. So the backup has **two parts**: (1) the account gets an **email and a password**, so the same account can be opened on another phone (same id, same chats list); (2) a **key file** holds the private encryption key, sealed with a passphrase, so the old messages can be opened there.
- Firebase Console (once, by the owner): **Authentication -> Sign-in method -> Email/Password -> Enable** (leave "Email link" off) -> Save. Without it the app says "Email sign-in is not enabled in Firebase". Nothing else in Firebase, **no change to `firestore.rules`, the Worker or Cloudflare**, no new permission in the manifest.
- Linking (Security centre -> **Account and backup**): email + password + the same password again -> `linkWithCredential` on the current account (the id does not change, `isAnonymous` becomes false). Rules (`data/Backup.kt`, 63 checks in `BackupTest`): a plausible email, a password of at least 8 characters that is not a very common one (`12345678`, `password`...) and not made of one or two repeated characters. There is a **"Send a mail to change the password"** button (Firebase's own mail; free). The checklist of the security centre now has two more points: **Account recovery (email)** and **Key file**.
- Key file: **Make a key file** -> a passphrase (at least 10 characters, twice) -> the system "save file" screen (the person chooses the place: phone memory, Drive, a flash drive...) -> the app writes it and **reads it back and opens it** to be sure it works. The file is text: `KHOSQKEY1` + `uid`, `pub`, `salt`, `iter`, `iv`, `data`. The private key (PKCS#8) is sealed with **AES-256-GCM**; the key comes from the passphrase through **PBKDF2-HMAC-SHA256, 210,000 rounds** with a random 16-byte salt (the passphrase is normalised to Unicode NFC, so the same words typed on two keyboards agree); the account id and the public key are bound into the seal, so changing a line of the file makes it fail to open; a crafted file with a huge `iter` is refused (so it cannot freeze the phone). Nothing is uploaded anywhere: the app never sees the file again after writing it, and **no passphrase is stored**.
- A new phone: the first screen has **I already have an account** -> email + password (**I forgot the password** sends the reset mail) -> the app signs in as the same account and **does not start yet** -> **Choose the file** + its passphrase -> the key is put back (`E2E.importIdentity`: the two halves must belong together, checked by signing and verifying; all keys worked out from the temporary identity are forgotten) -> the app starts and publishes the same public key as before, so **friends see no change** and the old messages open. The file must belong to the signed-in account (otherwise "This file is for another account"). **Continue without the file** is possible after a warning: the chats list comes back, but the old messages do not open and friends see "the safety number has changed". The key can still be put back later (Security centre -> **Restore the key from the file**, then close and open the app); friends then see the warning again.
- The empty anonymous account made at the first start of a new phone is deleted after the sign-in (if that fails it is only an unused empty account). Several phones can be signed in to one account; each needs the key file to read the old messages.
- Honest limits: **there is no way to recover a forgotten file passphrase** (not for me, not for anybody; it is only a locked file), and the password of the account is only reset through the email address, so the email must be one the person can still open. The email is **not verified** (no mail is sent at linking). The file is as strong as its passphrase: somebody who gets the file can try passphrases on their own computer (210,000 rounds slow this down, they do not stop a short or common passphrase). The messages that were sealed with the old key can only be opened with that key: **a key file made before some other key change is useless**, so make a new one after anything unusual. Verified marks of contacts (5b) and the other settings of the phone (SOS circle, lock...) are **not** in the file and have to be set again. Not tried on real phones from the build machine: the system save/open file screens (Drive, Samsung My Files), the Firebase email calls, and the 210,000-round stretching time on the old test phones (about a second is expected).
- New files: `data/Backup.kt`, `crypto/KeyFile.kt`, `ui/Account.kt`; changed: `crypto/E2E.kt` (the identity can now be exported and replaced), `data/Repository.kt` (link / sign in / reset mail), `ui/AppViewModel.kt`, `ui/Security.kt`, `ui/Home.kt` (the button on the first screen), `MainActivity.kt`, `data/Security.kt` (two more points), `Strings.kt` (English and Russian). A new APK is needed; the signing key is the same.
- Phone test: (1) Do the Firebase Console step. (2) Security centre -> Account and backup -> link an email (the checklist point turns green) -> make a key file (the list shows its date). (3) Best test of the whole way: install the app on a **second phone** (or remove and install it again), on the first screen tap **I already have an account** -> email and password -> choose the key file + passphrase -> the same chats list and the old messages open; a friend sees no "safety number changed". (4) Wrong password / wrong passphrase give clear messages. (5) Try the same without the file, then **Restore the key from the file**.

## Phase 5f (after the first phone tests: the chat follows new messages, photos open large)

- **The chat follows the newest message.** The list of a chat is upside down (the newest message is item 0), and Compose keeps showing the same older message when a new item is put in front of it, so a new message stayed out of sight below. Now the chat jumps down (a short scroll) when **I send** a message, and when a message **arrives while the chat shows the bottom**; it also follows the "typing" bubble when it shows. It **stays where it is** when I have scrolled up to read old messages (the round "down" button is there as before), while I am searching, and when the chat has only just opened. The "bottom" is read while composing, i.e. as the list was laid out before the new message moved it; a jump that is still on its way counts as the bottom, so two messages in a row do not stop the first jump. The decision is in `data/ViewLogic.kt` (`ChatScroll`), `ViewTest` has 45 checks for it.
- **A photo of a chat opens large.** A tap on a photo in a chat opens `ui/Viewer.kt` (`ImageViewer`): the whole screen, black; **two fingers zoom** (1x to 5x, the spot under the fingers stays under them), **one finger moves** a zoomed picture (never past its edges), **double tap** zooms in (2.5x on the tapped spot) and back, **one tap** hides or shows the top line (the date and the cross), the cross or the back button closes. A long press on a photo still opens the message menu. The grid of the chat's photos ("Media") uses the same viewer. The viewer is a separate window that inherits the screen-capture protection of the app (Security centre), like the other windows. The zoom arithmetic is in `ZoomMath` (pure, tested).
- **Profile photos open large.** A tap on the photo opens it in the same viewer: **my own photo** in the Settings tab (the camera badge still changes it; with no photo a tap on the circle still picks one), **a contact's photo** in the contact card (tap the name in the chat), **a group's photo** in the group card. Lists (chat list, headers) are unchanged: a tap there opens the chat as before.

## Phase 5g (QR codes: add a contact and check a key face to face)

- **What it is.** Every person has a QR code. It holds three things, none of them secret: the **ID** (handle), the **account id** and a **fingerprint of the public key** (the first 16 bytes of SHA-256 of the key as it is published, 22 characters). The text is `KHOSQ1/<handle>/<uid>/<fingerprint>` (under 100 characters, so the code is small and easy to read). The rules are in `data/QrLink.kt` (`QrLogic`, pure; `QrTest` has 40 checks: the shape, every kind of bad text, forged codes).
- **Why it helps.** The chats are end-to-end encrypted with each person's public key, which the app takes from the server (and pins on first sight). A server that was tampered with could hand out a false key. A code that is **shown face to face** says what the real key is. The app asks the server for the person's key, hashes it and compares: the same fingerprint means the key is the real one; a different one means **somebody may stand between the two people (or the code is forged)** and nothing is added or verified.
- **Add a contact by QR** (Home -> "+" -> **New contact**): the buttons **Scan a QR code** and **My QR code**. After a scan the app finds the account by the ID in the code, checks that the ID and the account id belong together, checks the key, starts the chat (the same "wants to write to you" request as by ID) and marks the key as **verified** (the blue mark). If anything does not match, the contact is **not** added and the text says why.
- **Check a contact you already have** (the contact card, tap the name in the chat): **Verify with a QR code** and **Show my QR code**, next to the 8 pictures of 5b. A code of another person than this contact is refused ("This is not the code of ..."). A scan also settles a "safety number has changed" warning when the new key is the one the person shows.
- **One direction per scan, said honestly.** When I scan the other person's code, I know their key is real, so **what I write to them can only be read by them**. For me to be safe from their side too, they must scan **mine**. Both ways in one go: show a code, scan, then swap. The card says so when a contact was verified by a scan ("... they should scan your code as well"); the 8-pictures way (both compare) stays as it was. The mark belongs to the keys as before: when either key changes, the verified mark goes away.
- **Scanner and code drawing.** The scan uses the **code scanner of Google Play services** (`play-services-code-scanner:16.1.0`): its screen belongs to Google's service, so the app needs **no camera permission** for it, nothing is sent anywhere (the code is read on the phone) and the app has no camera code to look after. The manifest gets one line that asks Google Play services to fetch the scanner when the app is installed (`com.google.mlkit.vision.DEPENDENCIES` = `barcode_ui`); without internet the first scan may have to wait. The code is **drawn** with ZXing core (`com.google.zxing:core:3.5.3`, pure Java, about half a megabyte), black on a white card whatever the theme. A phone without Google Play services cannot scan (it can still show its code and use the 8 pictures).
- **What the code does not do.** It does not carry the private key or any message. Anybody who photographs it learns the ID and the account id, which anyone who knows the ID can already learn; they cannot pretend to be the person (the key on the server must hash to the fingerprint, and the person's own private key is needed to read anything). Show it to people you have met, as with an ID.
- No change in the database rules, the Worker, Cloudflare or the signing key. New: `data/QrLink.kt`, `ui/Qr.kt`; changed: `crypto/E2E.kt` (`serverKey`, `verifyByQr`, `verifiedByQr`), `ui/AppViewModel.kt` (`addByQr`, `verifyScanned`), `ui/Home.kt`, `ui/Verify.kt`, `ui/Settings.kt`, `ui/Screens.kt`, `Strings.kt`, `app/build.gradle.kts` (two libraries), `AndroidManifest.xml` (one meta-data line). The Build APK step downloads the two libraries from the internet, as it does for the others. A new APK is needed.
- Not tried from the build machine (no Android, no internet there): the two libraries compile and run, the first start of the Google scanner on the test phones (A12, S10+), how well a code on a screen is read at different brightness, and the whole way between two real phones. The logic that decides is checked (QrTest, the key checks); the screens are not.
- Phone test: (1) on phone A: Home -> "+" -> New contact -> **My QR code**. (2) on phone B: New contact -> **Scan a QR code** -> scan: the chat with A opens and the blue mark is on A's name. (3) swap: B shows, A scans. (4) on A's phone the contact card of B shows "verified by a code" text. (5) a code of somebody who is not in the app, or any other QR (a web address), gives "This is not a KHOSQ code". (6) scan your own code: "This is your own code".

## Phase 5i (a faster place, and "Check the notifications" for phones that close apps)

- **A faster place.** Sending a location waited for the GPS alone, which indoors can take 10-20 seconds or more, and showed only a short message. ## Phase 6a (the web version, step 1: sign in with a QR code)

- **What it is.** A web page (`docs/`, served by GitHub Pages at `https://styop641121.github.io/Khosq-App/`) that you sign in to like WhatsApp Web: the page shows a QR code, the phone scans it (**Settings → Security → "Link a browser"**), and the browser is signed in as the same person **with the same private key**. This step is the **foundation**: sign-in, the encrypted key transfer, the key kept in the browser, log out. The page then shows who you are and three checks. **Chats, sending, groups, media, calls and the rest come in the next steps**, one by one (a full copy of the app is the goal).
- **How the key travels (nothing readable ever touches a server).** (1) The page makes a one-time key pair in the browser (P-256, **non-extractable**) and shows `KHOSQ-LINK1/<id>/<public key>` as a QR code. (2) The phone scans it and shows a **4-digit number**; the page shows the same number. You compare them (if someone put a different code in front of you, the numbers differ). (3) After "Link" the phone makes its own one-time key, agrees a secret with the page's public key (ECDH), derives an AES-256 key (HKDF-SHA256, salt = the code id) and **encrypts** the identity (uid, public key, **private key**, a random proof `r`) with AES-GCM. (4) The phone leaves the sealed packet in the Worker's post box (`links/{id}` in Firestore, **no Firestore rule**, so only the Worker can touch it; it lives 3 minutes; the first phone to answer wins). (5) The page collects it, opens it (only the page's non-extractable key can), and sends the Worker the proof `r`. (6) The Worker checks `SHA-256(r)` against the phone's `rh`, then makes a **Firebase custom token** for that uid (one time only) and the page signs in with it. (7) The private key is saved in the browser's IndexedDB **as a non-extractable key**: scripts on the page can use it but cannot read it out.
- **What the Worker sees.** Only encrypted bytes, the code id and the proof. It cannot open the packet (it never has the page's private key). The packet is useless without the page that made the QR code.
- **The phone.** `data/LinkLogic.kt` (pure: reads the QR code, the 4 digits, seals), `push/LinkClient.kt` (sends it), `ui/Link.kt` (the row, the camera scan, the confirmation window with the number). The same protocol is written again in `docs/link.js`; **the two were tested against each other** (the page's real WebCrypto opens what the Kotlin code sealed).
- **The page** (`docs/`): `index.html` (a strict Content-Security-Policy: scripts only from itself and Google's Firebase address), `app.js` (screens and flow), `link.js` (the protocol), `qr.js` (its own QR encoder, no outside library), `store.js` (IndexedDB), `i18n.js` (Armenian, English, Russian), `style.css` (light and dark), `config.js` (the Worker's address). The Firebase web library is loaded from Google's address; the Web API key and project id come from the Worker (`/link/config`), so nothing is copied by hand.
- **The Worker** (`worker/worker.js`, one new block): `/link/config`, `/link/poll`, `/link/put`, `/link/finish`. **No new secret and no new setting**: it uses the same `SA_JSON` and `API_KEY`. Only the pages at `https://styop641121.github.io` may call it from a browser (more addresses can be added with a `WEB_ORIGINS` variable). Rate limits per address and per person; at most 4 KB per request.
- **Cost.** The page asks the Worker every 2.5 s only while it is visible and waiting for a phone; a code lives 100 s. One sign-in is about 40 requests, 3 Firestore writes and a few reads. Free plans are enough.
- **Honest limits.** (1) **No remote "log out that browser"** yet: Firebase would have to cancel the account's sessions, which would also sign out the phone. To remove a browser, press **Log out** on that page (it deletes the key there). If a computer is lost, treat that browser as lost until the remote removal is added (a list of linked browsers with remote removal is planned for a later step). (2) Anyone who sits at a **signed-in** browser has your account in it; log out on shared computers. (3) The page runs on GitHub Pages; if GitHub's address were hijacked, the page's code could be replaced. Pin it to your own domain later if that matters. (4) **Browsers**: the page needs WebCrypto with P-256 and IndexedDB. **Safari clears a site's stored data after 7 days without a visit** (its tracking protection), so on Safari you may have to scan the code again after a week away; "Private" windows forget the key when closed. (5) Tested in a real Chromium with a pretend Worker and a pretend Firebase (**13 browser checks**, **121 Worker tests**, the Kotlin sealing against the page's WebCrypto, the QR code read back with a scanner). **Not tested: the real Firebase library from Google's address, the real Firebase sign-in with the custom token, a real phone scanning a real screen.** If the API key of the project is restricted to the Android app, the web sign-in will be refused (see the instructions).

The person told is the author found there; the sender's name and the group's title come from the chat document, **not from the request**, so nobody can sign a reaction with another name. A bad message id is answered with 400 and nothing is read. The push carries: the emoji, the sender's name, the group's title, the message id, no text of any message (the reaction itself is not encrypted, as before: it is stored as a plain emoji).

## Phase 6e (the web version, step 5: sending a photo and a voice message)

- **What it is.** Two new buttons next to the message box: a **camera** (left) and a **microphone** (right). **Photo:** press the camera and choose a picture (or paste one into the box: a screenshot, a copied picture). It does **not** go at once: it waits in a bar above the box (a small picture, its size, **Send** and a cross), so you can look at it first. **Voice message:** press the microphone, the browser asks for the microphone, the bar shows a red dot and the time, **Send** ends the recording and sends it, the cross throws it away. Esc also throws away what waits (and does not close the chat), the focus goes to Send when the bar opens and back to the box when it closes. Both buttons are off when no chat is open and when the box is closed (blocked chat, a request I have not accepted, a group for admins only, a changed key that is not acknowledged); a waiting photo or a running recording is dropped when the box closes and when you open another chat (**the microphone is let go at once**: the browser's "microphone in use" sign goes off when you cancel).
- **Made the way the phone makes them.** Photo: the longer side at most **1280 px**, a JPEG that is shrunk (quality 80, 70 … 30) until it is at most **700 KB**, refused above **900 KB**; a file that is not a picture, one the browser cannot open or one bigger than 40 MB is refused with a message; a small picture is not made bigger; drawing it on a canvas also **drops everything else the file held** (the place where it was taken, the camera's name); a see-through picture gets a white background. Voice: **AAC in an MP4 file**, 32 kbit/s (about 4 KB a second), the same loudness bars as the phone (40 digits 1..9, the same arithmetic as the phone's `VoiceRecorder.wave()`), at least **1 second** ("too short" otherwise), it **stops by itself at 850 KB** (about 3½ minutes) and says so, and one over 900 KB is not written.
- **What is written is what the phone writes** (`Repository.sendMedia`). One batch: the message `{from, text: "", kind: "img" | "voice", dur (0 for a photo), wave (voice only), data (the sealed bytes), ts, e: true, w (a group: the wraps)}` and the chat `{lastText: "📷" | "🎤", lastEnc: false, lastKind, lastTs, lastFrom, unread.<others> +1}`. The bytes are sealed exactly like a text (AES-256-GCM, field `"d"`, the message key: the chat key for one-to-one and saved, a message key wrapped for every member in a group), so the server never holds a readable picture or voice note; **no file name goes anywhere**. The push is the push of a message (my name or the group's name, no text) after the server has it; none for saved messages, which also have no counter. A reply that is being written stays and is **not** attached to a photo (as on the phone). Pressing Send twice sends once.
- **If it cannot be sent.** A refused write takes the message away from the screen and says "was not sent"; if somebody in the chat has no encryption key yet nothing is written, not in the clear either, and the **photo stays on the bar** so it can be sent after. A recording that could not be started says why in words: microphone refused, no microphone, another error. **A browser that can record only WebM (Firefox) says "cannot record in a format the phone plays"**, and the microphone is not even opened: a voice message the phone cannot play would be worse than none. Photos work in every browser.
- **A bug found and fixed here:** my first version of this step used the name `clock` a second time inside `shell.js`, which **replaced the time formatter** and put "29928660553:09" under every message. The screenshot showed it (the logic checks did not); it is fixed and the test now checks the time under the bubble.
- **Cost on the free plan.** One photo or voice message = **2 writes** (message + chat) + the Worker call; no new reads. **Network:** the message document holds up to ~900 KB, and every device that has the chat open downloads it once (Firestore's free plan has 10 GB a month of outgoing data: about 14,000 downloads of a 700 KB photo, counted per device that opens it). The phone shows my photo / voice from the message itself, no Storage is used.
- **Tests.** (1) `worker/webmedia.test.mjs` (**9 tests**) with `worker/web.media.fixture.json`: the exact fields of a photo and of a voice message in a one-to-one chat, the other person opens the bytes; only valid bars are written; a group (the message's own key, wrapped for all three, each opens it); saved messages (only I open it, no counter, no push); the push after the server has it (held back by the test); what is refused writes nothing (a wrong kind, no bytes, too big, no key for somebody, a closed chat); the size rule (1280, the shape kept, never bigger); **the loudness bars equal the answers of the phone's real Kotlin code for 13 recordings**; the voice format. (1b) A **one-off cross-check with the phone's real Kotlin crypto**: photos sealed by the page (one-to-one, group, saved, empty and large) were opened by the Kotlin code, **73 checks OK, 0 failed**. (2) Real **Chromium**, `e2e_media` (**26 checks**; the microphone and the recorder are pretend because the test browser has no AAC encoder: what is checked is everything around them): both buttons' states, a big photo shrunk to 1280×853 under 700 KB and **Bob opens a real JPEG**, the exact writes, the time under the bubble, the chat-list line and the push, a text file / broken picture / 41 MB file refused, a small picture kept, a noisy picture shrunk by quality, paste of a picture and of text, cancel / Esc / another chat / blocked chat drop the photo, a text in the box is not touched, a group (Bob, Carol and I open it), a double press, a reply that stays, saved messages, a refused write, no key, the recording (asks once, 32 kbit/s AAC, counts seconds, Bob opens **exactly what was recorded**, the microphone and the meter are let go), cancel and Esc and another chat end it, too short, a refused / missing / failing microphone, WebM only, the size limit (stops by itself, can still be sent), over 900 KB (not written), the microphone allowed only after the person has left the chat (let go at once), a phone-sized window and the three languages. **Mutation checks:** 23 deliberate bugs were all caught (wrong field sealed, no size limit, no chat-list line, bars not checked, a push for saved messages, no unread counter, a duration for a photo, no quality loop, no shrinking, linear bars, WebM accepted, no size cap for a recording, the microphone kept after cancel, the microphone let go twice, a photo that follows me to another chat, a photo kept when the box closes, a recording under a second sent, Esc closing the chat, pasted text swallowed, no focus back to the box, a microphone allowed too late and kept on, a wrong "too big" message, a photo dropped when nothing was sent). Two of them first **survived** and showed weak tests (the quality loop and the late microphone); the tests were strengthened and now catch them. One more thing the mutation run showed: a double press on Send is stopped by **three** independent layers (the button is off while sending, a guard in the handler, and a check that the photo is still the one waiting), so removing one layer cannot be seen from outside; removing the first two still sends once. Re-run and passing: `node --test` (**178**), `e2e_send` (**30**), `e2e_act` (**30**), `e2e_chats` (**27**), the sign-in test (**12**).
- **Not tested here (cannot be):** a **real** browser's AAC encoder and microphone (Safari and a current Chrome should record AAC in MP4; I could not run either), **whether the phone plays a voice message recorded in the browser** (a browser's MP4 is "fragmented"; Android should play it, but only a real phone proves it, and the time bar of the phone's player may differ), whether the phone shows a photo from the page the same way as its own, the real Firestore rules for these writes (the fields are the phone's), Safari itself. **If the phone does not play a voice message from the page, tell me, and I will turn the microphone button off on the page until it is fixed (photos do not depend on it).**

## Phase 6f (the web version, step 6: new chats, requests, blocking and the chat list's menu)

- **What it is.** (1) A round **"+" button** beside my name opens **"New contact"**: type a friend's **ID** (what the phone allows in an ID box: small letters a-z, digits, `_` and `-`, at most 30; anything else is not let in) and press **"Find and start a chat"** (or Enter). (2) A **request** from somebody (a chat they started with me and I have not accepted) now shows a bar under the messages, **"X wants to write to you" with Block and Accept**, and no message box until I accept. (3) **Blocking:** a person I blocked shows **"You blocked this person" with Unblock**; a person who blocked **me** only gets the plain line "Writing is off: this chat is blocked." (4) The **chat list has the phone's menu**: **Pin / Unpin, Mute / Unmute (not for saved messages), Mark as read / Mark as unread / Remove the unread mark, Archive / Unarchive, Block / Unblock (one-to-one chats only)**. With a mouse a **"⋯" button** shows on the row under the pointer (in the place of the time, so it never covers the unread count) and a **right press** opens the same menu; the **header's "⋯"** opens it for the open chat (this is the way on a touch screen, where the row button is hidden; a long press on a row also sends the "context menu" event, but that was tested only as the event, not with a real finger).
- **New chat, step by step.** The page reads `handles/<id>` and then `users/<uid>` (2 reads) and then asks whether the chat is there (1 read). **My own ID**, an **empty** box, an **ID nobody has** and **a server that cannot be asked** each give their own short message in the same window, with nothing written. **A person I already have a chat with is only opened and nothing is written**, whatever state it is in (in the archive, a request, blocked): the filter switches to "Archive" if the chat is there. A **new** person: **one write**, the pending request, exactly the phone's (`Repository.startChat`): `chats/<smaller id>_<larger id> {members: [me, them], names, handles, status: "pending", requester: me, pv}` (their picture version is added when they have one, so the picture shows at once; the phone fills it in later). The chat opens, its row is scrolled into view (a chat with no message yet sits at the bottom of a long list), the **cursor goes into the message box** (not on a touch screen), the row says **"Waiting for approval"** and a note under the messages says "Waiting for X to accept your request". As on the phone, **the one who asks may write the first message** at once. Making the request pushes nothing (there is no message); the first message pushes as any message does. A double press (button or Enter) makes **one** request; closing the window while it works means the chat does not open by itself later; a refused write leaves nothing in the list.
- **A request to me.** The warning text is the phone's: first, if the name **copies the name of one of my contacts** ("Attention: this name is the same as the name of your contact …", or "very similar … one letter differs"), then "This is a stranger. If they ask for money, a code or a password, or send a link, do not believe them." The lookalike check is a **port of the phone's `VerifyLogic`** (Armenian and Russian letters by sound, case, accents, word order: "Petrosyan Armen" meets "Պետրոսյան Արմեն"; a short name must be the same, a name of 9 or more letters may differ by one letter); **only my accepted one-to-one chats count as contacts** (not requests, groups or saved messages). **The page does not know which contacts the phone has marked "verified"** (that mark lives on the phone), so it uses only the two softer warnings. **Accept** writes just `{status: "active"}`; **Block** writes `{"blocked.<me>": true}` (the field is deleted to unblock). Both are only possible in the cases the Firestore rules allow: Accept only for a request made by somebody else, a block only on my own key, never in a group or my saved messages.
- **My lists** (pinned, muted, archived, "marked unread") are arrays in `prefs/<me>`, changed with **one small `arrayUnion` / `arrayRemove` merge each** (exactly the phone's `setPref`), so a pin made on the page shows on the phone and back. **"Mark as read"** does what opening the chat does (my counter to 0, the other side's ticks turn) and takes the unread mark off. **"Mark as unread"** shows a **dot** (no number) until the chat is opened or the mark is removed. A **refused write is taken back** on the screen and says "The change was not saved…".
- **Cost on the free plan.** A new chat: 3 reads and 1 write. Accept, Block, Unblock, a pin / mute / archive / mark: **1 write** each. The Worker is not called for any of these.
- **Found and fixed while testing:** after "New chat" the browser gave the focus back to the "+" button (so typing did nothing), now the box gets it; a new chat sat out of sight at the bottom of the list, now it is scrolled into view; the first version of the row's "⋯" button covered the unread count, now it replaces the time; and **a small race when the "New contact" window is closed with Esc** (the dialog's "close" event comes a moment after Esc, so a slow answer arriving in between could still open the chat; found because the test failed one run in four; the window now forgets the search at Esc / Cancel at once, and the test passed 10 runs in a row after).
- **Tests.** (1) `worker/weblookalike.test.mjs` (**5 tests**) with `worker/web.lookalike.fixture.json`: the page's name arithmetic gives **the same answers as the phone's real Kotlin `VerifyLogic`** (the fixture is the Kotlin program's own output, run with the Kotlin compiler). ## Phase 6g (the web version, step 7: forward, star and pin a message)

- **What it is.** The menu of a message (the "⋯" button next to it, or a right press) has three new items: **Forward…**, **Star / Unstar** and **Pin message / Unpin message**; the menu of my own message now has five items (Reply, Forward…, Star, Pin message, Delete for everyone). (1) **Forward…** opens a window with the chats the message can go to (tick one or several; the button says "Send (N)") and writes a **copy** into each: the same kind, text, picture or voice note, marked **"↪ Forwarded"**; a quote, the reactions and the "changed" mark are not copied. The window offers a **group or an accepted chat I may write to, and my saved messages**: not a chat I blocked, not a request of mine that is waiting, not an announcement group where I am not an admin. A message of a chat where I cannot write (a blocked chat, an announcement group) **can** still be forwarded out of it. (2) **Star** puts a **★** on the message (the mark shows to me only) and on my list; a **★ button in the chat list's top bar** opens **"Starred messages"**: who wrote it, in which chat, the text (or "Photo", "Voice message" …) and the time; pressing a line **goes to the chat and to the message** (older pages are loaded, up to five, until it is there; a message too far back says so and tells you to press "Load earlier messages"; a chat that is gone says so inside the window), the **★ at the right of a line** takes it off the list. (3) **Pin** puts a bar **above the messages** with the pinned text ("Pinned message"); pressing it goes to the message and lights it; **✕** takes the pin off; a photo, a voice note, a place and a sticker show by their sign. The pin is **one per chat and shown to everybody**; in an announcement group only the admins pin and see the ✕.
- **What is written is what the phone writes.** **Forward** (`Repository.forward`): one batch, the message `{from, text (sealed, field "t"), kind, dur, fwd: true, ts, e: true, w (a group: the wraps), data (a photo or voice note: the bytes sealed again, field "d"), wave}` and the chat's list line (the first 80 characters of a text, sealed, or the sign of a photo / voice note / place / sticker) with the other people's unread counter +1, and then the Worker's push as for any message. **A copy is sealed again for the people of the chat it goes to**, so a forward from a one-to-one chat into a group works for every member. **Star** (`Repository.setStar`): `prefs/<me>/stars/<chat id>~<message id> = {chatId, chatName, fromName, mine, kind, text, enc, ts, at}`; the text (only of a text, 600 characters at most, or a sticker, 40) is **sealed with the key made from my own key pair** (label `star|<chat id>~<message id>`), so even the server's copy of the list is unreadable and **the phone and the page open each other's stars**; a photo, a voice note or a place keeps only its kind. **Pin** (`Repository.setPinned`): one update, the chat's `pin = <message id>` (the field is deleted to take it off). A star of an SOS card, a call, a group line, a deleted message or one I cannot read is not offered.
- **Where the page differs from the phone, on purpose.** (a) The phone stores a star's text **in the clear** when it cannot seal it; **the page never does**: it writes nothing and says "Not starred: the message could not be sealed with your key. Nothing was stored in the clear." (b) The page does **not forward a poll** (it does not show polls yet; a poll can still be starred); the phone copies one. (c) The page's list of targets also leaves out **an announcement group I cannot write in** (the phone offers every group; both leave out a chat I blocked and a request that is waiting). (d) When the pinned message is older than the loaded ones the page **fetches that one message by its id** to show the bar; the phone shows the bar only when the message is loaded. (e) A forward to a **one-to-one chat whose person's key has changed** (and I have not accepted the change) is **stopped and told** by the page; the other chosen chats go on (the phone's forward does not look at this). (f) When the page cannot seal for somebody of the target chat it writes **nothing, not even in the clear**; the phone's own comment says it then sends without encryption.
- **Cost on the free plan.** Star / unstar: **1 write**. Pin / unpin: **1 write**. Forward: **2 writes per chosen chat** (message + chat) and the Worker call; a chat's people's keys are looked at once. The starred list is **one live query** (the newest 300 stars), so opening it reads at most 300 small documents; an old pin is **1 read** (the message by its id), once per pin.

## Phase 6h (the web version, step 8: voice and video calls)

- **What it is.** In a one-to-one chat the header has two new buttons, **a telephone (voice call)** and **a camera (video call)**. They show only where the phone shows its own (`canCall`) and where the Firestore rules allow a call: a **one-to-one chat that is accepted (status active) and not blocked**; not a group, not my saved messages, not a request that has not been accepted, not a blocked person (the buttons go at once when somebody is blocked while the chat is open). A small **call window** floats over the page, **above the box to write in** (on a phone-sized window: a band along the top for a voice call, the whole screen for a video call), so a voice call can go on while the chats are read and written. It shows the other person's name and picture and what is happening: **Calling… / Incoming call (or Incoming video call) / Connecting… / a running timer / the reason a call ended** (Call declined, No answer, Could not connect, Connection lost, Answered on another device, "Allow the microphone…"), with the buttons **Answer, Decline / Hang up, Mute / Unmute and Camera off / on** (every one has a spoken name for a screen reader, and the status is announced). A video call shows the other person's picture large and mine small in the corner (mirrored, silent); the camera button really switches the camera track off (the sound goes on), the mute button the microphone track.
- **Ringing.** The page **listens for calls to me while it is open** (one query: `calls where callee == me and state == "ringing"`), rings with a **ring made by the browser's own sound engine (no sound file)**, **flashes the tab's title "📞 Name"**, and **closes a window that has the page locked** (the profile, the list of people to forward to …) so the call can be seen and answered. The caller hears a calling tone while it rings. **The browser lets a page make sound only after the person has touched it once** (a click or a key): until then the ring is silent but the window and the flashing title show the call; once you have clicked anywhere on the page, the next beat of the ring is heard. A call that is **answered on another device of mine** (the phone, another tab) stops ringing here ("Answered on another device").
- **What is written is what the phone writes** (`CallManager.kt`), so a call between the page and the phone is the same call as one between two phones. The call is one document `calls/<id> = {caller, callerName, callee, calleeName, kind: "audio" | "video", state: "ringing" | "accepted" | "declined" | "ended" | "missed", ts, offer: {type, sdp}, answer: {type, sdp}, dur}`, and every network address a side finds is one small document `{sdpMid, sdpMLineIndex, sdp}` in `calls/<id>/callerCandidates` or `calleeCandidates` (the caller keeps its addresses until its call document is there: the rules read the document first). The sound and the picture go **straight between the two devices (WebRTC, encrypted by the browser itself)**; only when no direct way exists do they go through the relay (TURN) whose keys the Worker holds (`POST {type: "ice"}`, asked for in the background at most every six hours, and the page uses what the Worker gives (the same keys the phone uses); when the Worker has no keys or fails, the phone's free fallback servers are used, port 53 is left out as on the phone). **The caller** writes the call document, wakes the other phone through the Worker (`POST / {chatId, type: "call", title: my name, body: "📞" or "📹"}`, once, after the document is there), and at the end writes the **line in the chat** (**"Voice call · 1:05", "Video call · …", "Missed call", "Declined call", "Cancelled call"**) and the length in the document; a **missed** call also sets the chat list's line ("📵 Missed call"). The one who was called writes only the answer (`answer` + `state: "accepted"`) or `declined`.
- **Limits, as on the phone.** The caller gives up after **45 s** ("No answer", `missed`); an answered call that does not connect is ended after **30 s**; a connection that drops may come back within **8 s**; a ringing document older than **2 min** is not rung for; a second call while I am in one is **declined at once** ("busy"), and I cannot start one while in one (a small message says so); a call document of **more than 200 000 characters** or **without an offer** or **from myself** is not rung for. A call that **fails or drops writes no "ended"** (as the phone): each side ends it by its own timers and its own view of the connection.
- **Where the page differs from the phone, on purpose.** (a) **A page can ring only while it is open and awake.** A browser has no way to wake a closed page (that would need the browser's own push, which the page does not use), and the page already lets its server connection **rest after two minutes in a hidden tab** to save the free plan: so a tab you have left rings for **up to two minutes**, then hears nothing until you come back (the phone rings by push as always). A call that rings or goes on is **not** put to rest (the page checks again every two minutes and rests only when nothing is going on). (b) **No notification outside the page** (no Web Notifications); the window, the tone and the flashing title are all there is. (c) A video call can be **answered with the microphone alone** when there is no camera or it is busy (the screen says "no camera"); a **refused** camera or microphone declines the call, with the reason on the screen (the phone asks for the permission and stops). (d) A call that the caller **cancels while its document is still on its way** is ended as soon as it is there (the phone leaves it ringing). (e) **No group calls** (the phone has none either), **one call at a time**. (f) **Leaving the page in the middle of a call** (closing the tab, reload, signing out): the page tries to write the hang-up; a closing page cannot be sure it gets a write out, and in the test it **did not**: the other side noticed **after 14.9 s** through its own connection timers (the phone does the same when the network dies). **Signing out** hangs up properly (the write goes out first). (g) If **the phone and the page of the same account are both open**, both ring; the one that answers first wins and the page stops ringing; **the phone keeps ringing** (the phone's screen does not react to "answered on another device"; I have a small fix for the phone, not made, waiting for your word).
- **Cost on the free plan.** While the page is open: **one live query** (it reads a document only when a call to me appears). A call: **about 4 to 12 small documents of addresses per side** (4 in the test on one machine; a real network with a relay gives more), the call document (**1 write**), the answer / state / length (**2 to 4 small updates**), the line in the chat (**1 write**, 2 for a missed call), and the matching **reads** (each address document is read once by the other side, the call document a few times). That is **roughly 15 to 30 writes and about as many reads for a call**, against 20 000 writes and 50 000 reads a day on the free plan. The Worker: **1 push call per call** and **1 TURN-key request per six hours at most**.

## Phase 6i (the web version, step 9: groups)

- **What it is.** The page can now **make a group and run one**, with the same rights the phone has. (1) **New group:** in the window of the "+" button ("New contact") there is a link **"New group"**. It asks for a **name** (at most 40 characters) and for the people to put in (the list is **my accepted contacts**: not a request that is waiting, not a chat where somebody is blocked), and **"Create the group"** makes it: I am its only admin, and the new group opens by itself. (2) **Group info:** a group has a new entry **"Group info"** in its menu (from the chat header and from the list), and its **name and picture in the header open the same window**. It shows the picture, the name, the number of people, the description, and every member with their @ID and an **"admin"** mark. (3) **An admin** also sees: **Change the picture** / **Delete the picture**, **Change the description**, **Change the name**, the switch **"Only admins can write"** (the announcement mode), **Add a member** (my accepted contacts who are not in yet), and at each member **Make admin / Remove as admin** and **Remove**. Removing a person and leaving the group **ask first** (the phone's "Leave" asks, its "Remove" does not; the page asks for both because a mistaken tap there cannot be taken back with one tap). (4) **Everybody** can **Leave the group**. (5) What a member who is not an admin sees is the same window **without** the admin's buttons. (6) The window and the header follow the group **while it is open**: a rename, a new member, an admin made, the picture changed, the announcement mode switched on **on the phone** show at once; if an admin **takes me out** while the group is open, the window and the chat close and the page says **"You are no longer in this group"** (it does not say so when I left myself).
- **What is written (the phone's own shapes, field for field).** A new group is `chats/<new id>` with `{group: true, title, members: [me, ...], admins: [me], pv: {me}, names, handles, status: "active", lastText: "", lastTs, lastFrom}` and then the line `grp_created`. Every change is **one batch**: the change in the chat document and a line `{from: me, text: "", kind: "sys", code, arg, ts}` in its messages: `grp_added` (arg: the names, joined with ", "), `grp_removed` (arg: the name; members **and** admins lose the person), `grp_renamed` (arg: the new name), `grp_desc`, `grp_mode_admins` / `grp_mode_all` (the field `sendMode`), `grp_admin_on` / `grp_admin_off` (arg: the name), `grp_left`. The picture is `photos/<chat id>` `{data, ts: version}` written **first**, then `gpv: version` and the line `grp_photo` in one batch (so nobody is told about a picture that is not there yet); deleting it deletes the picture and sets `gpv: 0` (no line, as on the phone). **A member leaving** writes its line **first** and then `members` (and, when I was an admin, `admins`: the others stay admins, and when I was the only one the **first of the others takes over**, so a group is never without an admin while it has people). The lines are codes, so each phone and each page writes them **in its own language** (the page already did that for the phone's lines).
- **Nothing has to be handed out when people come and go.** A group has no shared key: every message is sealed with its own key, and that key is wrapped for the people the message is sent to. Adding a person changes who the **next** messages are wrapped for; a new member cannot read what was sent before, a removed member cannot read what is sent after. This is tested with the real sealing code: after adding Eve the next message opens for Eve, after removing Carol it is no longer wrapped for her.
- **The picture.** The page makes it the way the phone does: the **middle square**, **512 x 512 px**, a JPEG of **at most 70 KB** (best quality of 85, 75 ... 45 that fits; a very detailed picture falls back to 384 and then 256 px; one that does not fit even then says "The picture is too detailed"). The database refuses a picture of 90 KB or more, and the page never sends one. What is not a picture, or does not open, is told and nothing is written. The new picture is kept in this browser at once, so the list, the header and the window show it **without asking the server for it**.
- **What the page does not do, on purpose.** (1) **The invitation link.** The phone gets the link from the Worker (`/group/invite`, `/group/join`), and the Worker does not answer a web page (it allows pages only on its main address). Making the link available to the page needs a change in the Worker and a new deploy, so it is left for a later step and the window says: "An invitation link can only be made on the phone for now." (2) **A group call:** the phone has none either. (3) The page does not rename a person or change what the phone calls a contact. (4) A non-admin **who leaves a group in announcement mode** writes **only** the change of `members`, **without the line "left the group"**: the rules do not let a non-admin write any line there, so the phone's batch (the line first) would be refused as a whole and that person could not leave from the phone at all. The page therefore skips the line in that one case (the people see the member count change). **The phone has the same problem today** (`leaveGroup` writes the line first): a member who is not an admin cannot leave an announcement group from the phone; the phone is **not changed in this step**.
- **Safety.** Every name, title, description and ID somebody else wrote goes in with `textContent`, never as markup (tested with `<img onerror>` and `<b onmouseover>` in the title, a member's name and ID, and a description). The windows close when a call comes in (the page's rule for every window), and they open clean the next time (no old question, no old choice).
